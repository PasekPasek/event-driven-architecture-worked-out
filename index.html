event-driven architecture — worked out

How events actually flow, from a queue to an AI agent

A producer publishes a fact. Something, eventually, reacts to it. Everything else — brokers, partitions, retries, outboxes, multi-agent orchestration — is a variation on that one relationship. This page derives event-driven architecture from three things that are always true, then shows the same three things underneath a Kafka topic, an event schema nobody can migrate in one go, and a graph of AI agents reacting to each other's output.

01

Three things always true

Most explanations of event-driven architecture open with a diagram: boxes for services, arrows for messages, a cylinder for a queue. The diagram is a consequence. Start one level lower, with what makes something "event-driven" rather than just "asynchronous."

  1. A producer does not know who, if anyone, consumes an event it publishes. There is no return value and no caller identity — publishing is not the same operation as calling.

    Contrast a function call, where the caller knows exactly what it invoked and gets a value back. An event has none of that: zero, one, or a hundred consumers may react, and the producer's code is identical in every case.

  2. An event describes a fact that has already happened — price.changed, not change the price. A consumer that fails to process it does not un-happen it.

    This is why retrying a failed consumer is safe in a way retrying a failed RPC often isn't: the fact is still true, and processing it again should converge to the same result (see idempotency in §08).

  3. Coupling doesn't disappear, it moves: from "who do I call" (a function reference, a service URL) to "what shape do I emit, what shape do I expect to read." A schema change is now the thing that breaks consumers, not a moved endpoint.

Most of what follows is one of these three facts wearing a costume: a Kafka partition is fact 1 with a specific answer to "how many consumers, in what order"; an AI agent reacting to another agent's completion is fact 2, with the agent as both producer and consumer.

02

If you had to build it

An event needs something to hold it and something to eventually call the right reactions. Four drafts, each fixing the last one's problem, arrive at the shape every real broker takes.

Draft 1 — in-process, and gone the moment it's handled

import { EventEmitter } from "node:events";const bus = new EventEmitter();bus.on("price.changed", (e: { productId: string; price: number }) => {  console.log(`repricing ${e.productId} at ${e.price}`);});bus.emit("price.changed", { productId: "sku-1", price: 1999 });

Synchronous, at-most-once, and the event never existed outside process memory: crash between emit and the listener finishing, and it's simply gone. Fine for coordinating within one process; not durable enough for anything that must survive a restart.

Draft 2 — durable, but dispatched once

import { appendFileSync } from "node:fs";function publish(event: unknown): void {  appendFileSync("events.log", JSON.stringify(event) + "\n"); // durable  bus.emit("price.changed", event); // still only reaches whoever is listening *now*}

The fact survives a crash in the log. But dispatch is still a one-shot, in-memory broadcast: a consumer that starts five minutes later, or was down when it happened, never sees it. Durability of the fact and delivery to a consumer are two different problems.

Draft 3 — a reader tracks its own position

let offset = 0;function poll(): unknown[] {  const lines = readFileSync("events.log", "utf8").trim().split("\n");  const fresh = lines.slice(offset).map((l) => JSON.parse(l));  offset = lines.length; // remembered *after* processing, not before  return fresh;}

Now a consumer that restarts can resume from its own offset instead of the producer's broadcast moment. But note the comment: if the process crashes after reading a line and before persisting the new offset, that event is redelivered on restart. That's not a bug to fix — it's the origin of "at-least-once."

Draft 4 — acknowledge or redeliver

Give every delivered-but-unacknowledged event a deadline. If it isn't acknowledged before the deadline, hand it out again. That single rule is a broker's visibility timeout (SQS), its consumer group session timeout (Kafka), and its ack-wait (NATS JetStream) — three names for the same fix to the same problem Draft 3 exposed.

DraftWhat it fixesWhat it still can't do
1Reacting to something, at allSurvive a crash
2Surviving a crash (the fact is on disk)Deliver to a consumer that wasn't listening yet
3Resuming after a restartTell the difference between "processed" and "crashed mid-process"
4Redelivering what wasn't acknowledgedGuarantee a redelivery isn't processed twice (§08: idempotency)

What Drafts 1 and 2 look like when somebody ships them

Those four drafts are deliberately toys. Here is the whole event bus that 4th-devs — a real open-source agent-orchestration course, which the rest of this page keeps returning to — actually runs its agent system on: a sequence counter, a set of listeners, and a bounded buffer of everything already emitted.

let _seq = 0const listeners = new Set<Listener>()const buffer: AgentEvent[] = []export const emit = (type: string, data = {}): void => {  const event = { seq: ++_seq, type, time: new Date().toISOString(), data }  buffer.push(event)  if (buffer.length > MAX_BUFFER) buffer.shift()  for (const listener of listeners) listener(event)}export const subscribe = (listener: Listener) => {  listeners.add(listener)  return () => { listeners.delete(listener) }}export const replay = (): readonly AgentEvent[] => buffer

Source: 4th-devs, 05_01_agent_graph/src/events.ts.

That is Draft 1 and Draft 2 in about forty lines, and nothing more. emit doesn't know or care who is listening — fact 1, exactly, in one for loop. The bounded buffer plus replay() is a miniature durable log: a listener that attaches late is still handed everything that already happened. It never reaches Draft 3, because nothing here tracks a per-consumer position, and it never reaches Draft 4, because nothing acknowledges anything. For coordinating agents inside one process (§06) that is the correct amount of machinery, and the drafts above are the map of what you'd have to add the moment it isn't.

The edge, where this stops being enough

Notice what the bus cannot do: leave the process. The moment those events have to reach a dashboard in somebody's browser, the problem changes shape — one specific reader, across a process boundary, over a protocol. Every event-driven system eventually grows that edge, where events stop being broadcast to whoever cares and start being written down a socket to one identified reader, and the adapter between the two halves is one line: subscribe(event => res.write(event)). The left-hand side is this page. The right-hand side — Server-Sent Events, the wire format, reconnection, and how a model's tokens reach a screen — is a transport rather than an architecture, and it has a page of its own: streaming-worked-out.

03

Delivery guarantees, for real

"At-least-once" and "exactly-once" get repeated as marketing lines. Defined precisely, and checked against what four real systems actually document:

  • At-most-once — delivered zero or one times; a crash between send and receipt loses it silently.
  • At-least-once — delivered one or more times; a crash between processing and acknowledging causes a redelivery. The consumer must tolerate duplicates.
  • Exactly-once — the observed effect happens once, even if the underlying delivery is at-least-once underneath (achieved via deduplication or idempotent writes, not by magically never redelivering).
SystemDefault guaranteeOrdering
KafkaAt-least-once. Exactly-once needs an idempotent producer (enable.idempotence=true) and a transactional consumer (isolation.level=read_committed). Within one partition only (§04).
SQS standardAt-least-once, best-effort — duplicates and reordering both possible.None.
SQS FIFOExactly-once processing via deduplication. Within one Message Group ID only.
SNS standardAt-least-once per subscriber. None across the fanout.
SNS FIFOExactly-once, SQS FIFO subscribers only. Within one message group.
EventBridgeAt-least-once, automatic retry, per-rule DLQ. None.

Sources: Apache Kafka documentation — message delivery semantics; AWS SQS developer guide — FIFO queues; AWS SNS developer guide — FIFO topics; AWS EventBridge user guide.

None of these are run locally on this page — there's no browser-executable "real Kafka" to diff against, the way libuv could be diffed for the event loop page. These rows are quoted from the vendors' own documentation, not independently reproduced.

04

Ordering, partitioning and parallelism

"The event happened first" and "a consumer sees it first" are different claims. Nothing connects them unless a specific mechanism does.

Kafka orders messages only within a partition. A topic's messages across partitions have no defined relative order at all. A producer picks the partition via a key — same key, same partition, so events for that key are ordered relative to each other, but two different keys give no guarantee either way. SQS FIFO does the equivalent with a Message Group ID instead of a partition key: order is preserved only within one group.

Why partitions exist at all

Ordering is what partitions constrain; it isn't what they're for. A partition is the unit of parallelism. Kafka's own introduction puts the reason plainly: a topic is "spread over a number of 'buckets' located on different Kafka brokers," and that placement "is very important for scalability because it allows client applications to both read and write the data from/to many brokers at the same time." Within a consumer group, each partition is handed to at most one consumer, so the partition count is the ceiling on how many consumers can work that topic at once. Four partitions, four workers; a fifth worker sits idle.

Which makes the trade explicit, and it is the trade of this whole section: ordering and throughput are bought with the same currency. One partition gives you a total order over the topic and exactly one worker. A thousand partitions give you a thousand workers and no order worth the name. Picking a partition key is picking how small a scope you're willing to keep ordered — per customer, per SKU, per account — so that everything outside that scope is free to run in parallel. "Order events globally" isn't a requirement anyone can fill; "order events per customer" is a key.

Source: Apache Kafka — Introduction (partitioning, per-partition order, same key → same partition).

One consumer, or all of them?

A second distinction hides behind the word "consumer" and catches people out constantly, because both things get called a queue in conversation:

PatternWho gets the eventWhat it's for
Competing consumers Exactly one member of the group — SQS deletes it after a successful receive; a Kafka consumer group hands each partition to one member. Sharing work. Adding a worker adds throughput and changes nothing semantically.
Fan-out Every subscriber, each with its own independent copy and its own position — SNS subscribers, or separate Kafka consumer groups on one topic. Independent reactions to the same fact. Adding a subscriber adds behaviour, and the producer still doesn't know (fact 1).

The same Kafka topic does both at once, which is why the vocabulary gets muddled: consumers within one group compete, groups between themselves fan out. Two teams reading the same topic without noticing they're in the same group will silently process half the events each, and it looks exactly like random data loss.

05

What goes in an event, and what breaks when it changes

Fact 3 said coupling doesn't disappear, it moves into the shape of the event. That isn't a warning to file away — it's two decisions you make for every event type you ever define: what you put inside it, and what you do on the day you have to change it.

Three shapes, and what each one costs

Martin Fowler's names for these are the ones most teams end up saying out loud, so they're worth learning as names rather than as descriptions:

ShapeThe event carriesWhat it costs
Event notification {"orderId":"o-1042"} — the fact happened, here's the id. Every consumer has to call back to you for the details, so you've re-introduced exactly the runtime coupling fact 1 removed — and worse, the callback reads current state, which may already have moved past the event being reacted to.
Event-carried state transfer The fields consumers actually need: {orderId, total, currency, customerId}. No callback, and a consumer that was offline can catch up later without talking to you at all. In exchange every field is now a published promise — this is the row where the rest of this section applies.
Event sourcing Every change, kept forever; state is the fold over the log (§07). The log is the database, with everything that implies — compaction, replay cost, and no way to quietly fix a bad row.

Source: Martin Fowler — "What do you mean by Event-Driven?", which names these patterns (plus CQRS) and is where the terminology comes from.

The middle row is the one to reach for by default. The first is tempting precisely because the event is tiny and there is nothing in it to break — which is true, and the price is a synchronous call back into your service from every consumer on every event. That is most of what you were buying by going event-driven in the first place, handed back.

Then it changes, and you can't phone the people it breaks

Here fact 1 turns around and bites. You cannot coordinate a migration with consumers you cannot enumerate — the property that made publishing cheap is the property that makes changing expensive. Confluent's Schema Registry supplies the vocabulary teams end up using for this: BACKWARD compatibility "means that consumers using the new schema can read data produced with the last schema"; FORWARD means "data produced with a new schema can be read by consumers using the last schema." BACKWARD is its default. Adding or removing an optional field is allowed in both directions; that is the entire safe set.

One detail from those docs matters more than it looks, and the sandbox below is built on it: for JSON Schema, what counts as compatible "depends on both the compatibility policy and the content model (additionalProperties: true for open, false for closed)." Whether adding a field is safe is not a fact about your event. It's a fact about your consumers.

Source: Confluent Platform — Schema Evolution and Compatibility.

  1. Add, don't change. A new field is optional, and "absent" has to be a meaning you're willing to handle forever.
  2. Never rename in place. A rename is a delete plus an add wearing one commit message, and it breaks every reader of the old name simultaneously.
  3. Never retype in place. This is the one that fails quietly — see the third row of the sandbox.
  4. A genuinely breaking change gets a new event type, published alongside the old one until the old one goes quiet. Put the version in the type name (order.placed.v2), not in a field, so a consumer subscribes to what it can actually parse.

    07
    Event sourcing and agent state
    
  
    Nothing so far has stored "the current state" anywhere. It's derived: replay the
  event log from empty, and you have it. That's not an implementation detail — it's a deliberate
  trade of storage simplicity for compute-on-read.
    
  
    4th-devs writes exactly this: an append-only events.jsonl, one JSON
  object per line, that's never edited, only appended to:
    
  
    {"type":"task.completed","round":3,"at":"2026-02-16T12:00:00.000Z", "agent":"writer","taskId":"write-events-section", "data":{"turns":2,"estimated_tokens":1800,"actual_tokens":1690}}
    
  
    Source: 4th-devs, 03_02_events/docs/schemas.md.
    
  
    Two things fall out for free. Crash recovery: restart, replay the log, and the in-memory state is
  exactly what it was — there is no separate "did the state file get corrupted" failure mode, because
  there never was a state file, only the log. Observability: any question about "what happened, and
  when" is answerable by reading the log, not by having remembered to instrument that specific
  question in advance.
    
  
    It doesn't stay free. A log that only ever grows eventually costs more to replay
  than a snapshot would cost to load — which is exactly why Kafka ships log compaction (keeping only
  the latest record per key) as a first-class feature, not an afterthought. Snapshotting is named
  here, not built: out of scope for this page (§11).

      08
      Failure, retries, poison messages
      
  
      Every "at-least-once" system in §03 can redeliver. That's not a bug the consumer
  waits out — it's a contract the consumer must be written for: processing the same event twice has
  to converge to the same result (idempotency), or duplicates corrupt state.
      
  
      The real backoff formula this page's test-model.ts verified against
  4th-devs'
  recovery.ts:
      
  
      const delay = Math.min(15_000, 1_500 * 2 ** (attempt - 1));// attempt 1: 1500ms  2: 3000ms  3: 6000ms  4: 12000ms  5+: 15000ms (capped)
      
  
      One thing that formula does not have, and most production backoffs do:
  jitter. Every consumer knocked over by the same outage computes the same delay
  from the same formula, so they all come back at the same instant and knock the recovering service
  down again — a thundering herd, self-inflicted, on a schedule. The fix is to randomise: sleep a
  random duration up to the computed ceiling rather than exactly the ceiling. The formula is quoted
  here as 4th-devs writes it, which is jitter-free; adding it is a production change
  this page is naming rather than attributing.
      
  
      A message that keeps failing past a limit — 4th-devs caps auto-retry at 3 attempts —
  is a poison message: something is genuinely wrong with it, not just transiently unlucky, and
  retrying forever would starve everything behind it. Real brokers name this explicitly: SQS's
  redrive policy moves a message to a dead-letter queue after a configured
  maxReceiveCount; Kafka has no built-in DLQ, so the convention is application-level —
  publish the poison message to a separate <topic>.DLT topic instead of committing
  its offset normally.
      
  
      Sources: AWS SQS developer guide — dead-letter queues; Kafka's
  dead-letter-topic pattern is documented as a convention across Kafka Streams/Connect docs rather
  than a single core-broker feature.

      Idempotency, concretely
      
  
      Idempotency gets asserted on this page four times before here, so it had better be something
  you can write down. It is: processing the same event twice leaves the system in the same state
  as processing it once. Three ways to get there, in ascending order of how much bookkeeping
  they cost you.
      
  
      // 1. Not idempotent. A redelivery double-counts — silently, permanently, as real money.await db.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [amount, id]);// 2. Naturally idempotent: the event says what the world IS, not how much it moved.await db.query('UPDATE accounts SET balance = $1 WHERE id = $2', [balanceAfter, id]);// 3. Made idempotent with the event's own id — in ONE transaction with the effect.await db.tx(async (t) => {  const { rowCount } = await t.query(    'INSERT INTO processed_events (event_id) VALUES ($1) ON CONFLICT DO NOTHING',    [event.id],  );  if (rowCount === 0) return;                  // already handled; do not apply it again  await t.query('UPDATE accounts SET balance = balance + $1 WHERE id = $2', [amount, id]);});
      
  
      Option 2 is the one to design toward, and notice that it isn't a consumer fix at all — it's the
  §05 decision, made well. An event carrying a delta forces every consumer to be exactly-once
  or be wrong. An event carrying the resulting state lets a consumer be sloppy and still land
  correct. You can often buy idempotency for the entire downstream by changing one field in the
  payload, which is cheaper than buying it consumer by consumer.
      
  
      Two things about option 3 that get skipped. First, the transaction is not
  decoration: put the dedup insert in a different transaction from the effect — or in Redis — and you
  have rebuilt the dual write of §09, with a new failure where the marker says "handled" and the
  work never happened. Second, processed_events grows forever, so you prune it by age,
  which means your deduplication is exactly as good as that retention window and no better. SQS FIFO
  is honest about having the same limit: "within a 5-minute deduplication window, only one instance
  of a message with the same deduplication ID is processed and delivered"
  (AWS
  SQS developer guide — message deduplication ID). A duplicate that arrives six minutes late is
  not a duplicate as far as the broker is concerned.

      09
      The dual write: outbox and CDC
      
  
      Every example on this page has quietly cheated. Each one writes something down
  and publishes an event about it, and assumes both happen. They can't — not atomically.
  Your database transaction does not extend to Kafka, and the process can die in the gap.
      
  
      Write first, publish second: the process dies in between, and the order exists while nobody was
  ever told. Publish first, write second: you have announced a fact that isn't true yet, and may
  never become true. There is no ordering of the two calls that fixes this, because the problem isn't
  the order — it's that two separate systems can't agree without a transaction spanning both.
      

  
      The outbox: make it one write
      
  
      Stop trying to do two writes. In the same local transaction that stores the order, insert a row
  into an outbox table describing the event. One transaction, one system, atomic — the
  order and the intent to announce it either both land or neither does. A separate relay then reads
  unpublished outbox rows and pushes them to the broker, marking them sent.
      
  
      The crash doesn't disappear; it becomes survivable. Die before the relay runs and the outbox row
  is still sitting there on restart. Die after publishing but before marking it sent, and the relay
  publishes it twice — which is at-least-once again (§03), and exactly why the consumer has to be
  idempotent (§08). The outbox doesn't buy exactly-once; it buys "never silently lost".
      

  
      CDC: don't write the event at all
      
  
      Change-data-capture answers the same question from the other side. Instead of writing an event
  by hand, read the database's own replication log — Postgres' WAL, MySQL's binlog — and turn each
  committed row change into an event. The write is the event, so there is nothing to keep in
  sync and no outbox table to maintain. Debezium is the usual implementation.
      
  
      The trade is §01's fact 3, collected. With an outbox you choose the event's shape:
  order.placed, carrying the fields you meant. With CDC the shape is whatever your table
  looks like, so a column rename is a breaking change for every consumer — your schema stops being an
  internal detail and becomes the public contract. Cheaper to run, more expensive to evolve.

      10
      What you give up
      
  
      Everything up to here has been mechanism, and eleven sections of mechanism read
  like advocacy whether or not they meant to. So, the other side: this is the bill, and you pay it
  on day one, whether or not the decoupling ever pays you back.
      

  
      The call stack is gone
      
  
      "Why did this happen?" used to be answerable by reading a stack trace downwards. Now the causal
  chain is spread across processes and across time, and nothing reconstructs it unless you built
  that yourself: a correlation id threaded through every event and every log line, or a tracing
  system that does it for you. The demo below is the whole argument. Most teams discover the point
  it makes during an incident, which is the worst available moment to start adding correlation
  ids.
      

  
      "Find all callers" stops working
      
  
      The editor command that answers "what depends on this" is a feature of function calls. There
  are no callees to find behind emit('order.placed'); the new call graph is grepping
  for a string literal, and it misses anything that subscribes dynamically or builds a topic name by
  concatenation. Fact 1 is a runtime property you wanted. It is also a static-analysis property you
  have given up, and you gave it up for the whole codebase at once.
      

  
      Eventual consistency becomes somebody's UX problem
      
  
      The user clicks save, the write lands, the event publishes — and the list they are looking at is
  maintained by a consumer that hasn't run yet. That gap is now a product decision rather than an
  infrastructure detail: show a spinner, optimistically show the change in the client and reconcile
  later, or show stale data and accept the support tickets. There isn't a fourth option, and the
  choice belongs to whoever designs the screen as much as to you.
      

  
      Testing moves to the seams
      
  
      Every service's unit tests can pass while the system is broken, because the failure is a field
  one team renamed (§05) and another team read. Nothing inside either service is wrong. The tests
  that catch this are contract tests across the event schema, and they are the tests teams write
  after the first incident rather than before it.
      

  
      You now operate a broker
      
  
      A broker is a distributed system with its own upgrade path, its own disk pressure and its own
  pager rotation. Managed services relocate that work rather than remove it: partitions still need
  sizing (§04), consumer lag still needs alerting, and a dead-letter queue still needs somebody
  whose actual job is to look inside it. An unread DLQ is a data-loss bug that files itself neatly
  and waits.
      

  
      
    
      With a function callWith an event
      
    
      
      A stack traceA correlation id — if you added one beforehand.
      
      
      "Find all callers"Grep for a string, and hope nobody built the name dynamically.
      
      
      The caller sees the failureNobody sees it. The dead-letter queue does.
      
      
      Consistent when the call returnsConsistent eventually, and visibly so, on someone's screen.
      
      
      Deploy both sides togetherDeploy either side, and find out whether the schema held (§05).
      
          
  
      

  
      So when shouldn't you
      
  
      One service, one database, one consumer you own and deploy together: write the function call.
  It is better in every dimension that matters, and an event bus there buys you a decoupling you
  have no use for at the full price listed above. The bet pays when you actually hold what it buys —
  consumers you don't control, consumers you can't enumerate, consumers that have to survive your
  downtime, or one fact with several genuinely independent reactions. A useful test: if you can name
  your consumer, you don't have that yet.
      
  
      Events are a wager that not knowing your consumers will gain you more than not knowing your
  consumers costs you. It is frequently a good wager. It is never a free one.
      

  
      
    
      Sandbox — the same incident, with and without a correlation id
      
    
      Ten log lines from four services, interleaved the way they actually arrive.
    Answer this before touching the switch: which order got the "payment problem" email, and
    why? Then turn correlation ids on and answer it again. Same incident, same services, same
    logs — the only difference is one field somebody either threaded through beforehand or didn't.
      
    
      
      
    
      
    
      
      
      
      
    
      
    
        
    
        
  
        

        

        
  
        11
        The whole page in rules, and scope
        
  
          
    
        1. A producer doesn't know its consumers; an event is a fact, not a request — a failed consumer
    doesn't un-happen it.
          2. 
    
        2. "At-least-once" is the practical default everywhere (Kafka, SQS standard, EventBridge);
    exactly-once is achieved on top of it via idempotency or dedup, not by avoiding redelivery.
          3. 
    
        3. Ordering is scoped: to a Kafka partition, to an SQS Message Group ID — never to a whole topic
    or queue. A partition is also the unit of parallelism, so ordering and throughput are bought with
    the same currency: picking a key is picking how small a scope you keep ordered.
          4. 
    
        4. Consumers within one group compete for events; separate groups each get their own copy. The
    same topic does both, and confusing them looks exactly like random data loss.
          5. 
    
        5. Prefer an event that says what the world now is over one that says how much it
    moved: it makes every downstream consumer idempotent for free. Adding an optional field is the
    only safe change; a rename breaks everyone at once, and a type change breaks them silently. A
    genuinely breaking change is a new event type published beside the old one, because fact 1 means
    you cannot enumerate who to warn.
          6. 
    
        6. A multi-agent system is a DAG reacting to done events; the ready set is
    recomputed every round, the same shape as an event loop's phases one level up.
          7. 
    
        7. Agent state doesn't have to be stored directly — folding an append-only event log recovers it,
    for free, until the log itself needs compaction.
          8. 
    
        8. A consumer under at-least-once delivery must be idempotent; a message that keeps failing past
    a limit belongs in a dead-letter queue, not in an infinite retry loop.
          9. 
    
        9. You cannot write to a database and publish an event atomically. Make it one local write — an
    outbox row in the same transaction, or the replication log itself (CDC) — and let a relay do the
    publishing, or accept that a crash in the gap loses the event silently. The same rule governs a
    deduplication table: mark the event handled in the same transaction as the effect, or you have
    built the dual write again.
          10. 
    
        10. The bill arrives on day one: no stack trace, no "find all callers", eventual consistency
    visible on someone's screen, and a broker to operate. If you can name your one consumer, write
    the function call instead.
          11. 
  
        
  
        Left out, on purpose
        
  
        The outbox and change-data-capture got a section of their own (§09). Three more, named here
  rather than half-explained:
        
  
          
    
        • The wire. How events actually cross a process boundary to one identified
    reader — Server-Sent Events, its wire format, reconnection, and the way a model's tokens reach a
    screen — is a transport question rather than an architectural one. It used to live on this page
    and was pulled out, because two sections of HTTP mechanics on a page about architecture taught
    the wrong lesson about what event-driven means. It now has its own:
    streaming-worked-out. §02's
    subscribe(event => res.write(event)) is the seam between the two pages.
          • 
    
        • Sagas. Once a workflow spans services, there is no transaction to roll back.
    A saga replaces rollback with explicit compensating actions — refund the payment, release the
    reservation — which means designing the undo for every step, and accepting that the system is
    briefly, visibly inconsistent while it runs.
          • 
    
        • End-to-end exactly-once. §03's exactly-once claims stop at each broker's own
    boundary. Chaining two systems together doesn't compose their guarantees; the joint is where
    duplicates reappear, and idempotency (§08) is the only thing that actually travels.
