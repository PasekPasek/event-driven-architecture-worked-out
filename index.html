event-driven architecture — worked out

How events actually flow, from a queue to an AI agent

A producer publishes a fact. Something, eventually, reacts to it. Everything else — brokers, Server-Sent Events, streaming model output, multi-agent orchestration — is a variation on that one relationship. This page derives event-driven architecture from three things that are always true, then shows the same three things underneath a Kafka topic, an EventSource connection, and a graph of AI agents reacting to each other's output.

01

Three things always true

Most explanations of event-driven architecture open with a diagram: boxes for services, arrows for messages, a cylinder for a queue. The diagram is a consequence. Start one level lower, with what makes something "event-driven" rather than just "asynchronous."

  1. A producer does not know who, if anyone, consumes an event it publishes. There is no return value and no caller identity — publishing is not the same operation as calling.

    Contrast a function call, where the caller knows exactly what it invoked and gets a value back. An event has none of that: zero, one, or a hundred consumers may react, and the producer's code is identical in every case.

  2. An event describes a fact that has already happened — price.changed, not change the price. A consumer that fails to process it does not un-happen it.

    This is why retrying a failed consumer is safe in a way retrying a failed RPC often isn't: the fact is still true, and processing it again should converge to the same result (see idempotency in §09).

  3. Coupling doesn't disappear, it moves: from "who do I call" (a function reference, a service URL) to "what shape do I emit, what shape do I expect to read." A schema change is now the thing that breaks consumers, not a moved endpoint.

Most of what follows is one of these three facts wearing a costume: a Kafka partition is fact 1 with a specific answer to "how many consumers, in what order"; an AI agent reacting to another agent's completion is fact 2, with the agent as both producer and consumer.

One section is deliberately not. §05 is about Server-Sent Events, and SSE breaks fact 1: the server holds one specific client's connection and writes straight down it, knowing exactly who is on the other end. That's the opposite of a producer not knowing its consumers — which is precisely why it's worth a section. Every event-driven system eventually has an edge where events stop being broadcast to whoever cares and start being written to one identified reader. SSE is what that edge looks like.

02

If you had to build it

An event needs something to hold it and something to eventually call the right reactions. Four drafts, each fixing the last one's problem, arrive at the shape every real broker takes.

Draft 1 — in-process, and gone the moment it's handled

import { EventEmitter } from "node:events";const bus = new EventEmitter();bus.on("price.changed", (e: { productId: string; price: number }) => {  console.log(`repricing ${e.productId} at ${e.price}`);});bus.emit("price.changed", { productId: "sku-1", price: 1999 });

Synchronous, at-most-once, and the event never existed outside process memory: crash between emit and the listener finishing, and it's simply gone. Fine for coordinating within one process; not durable enough for anything that must survive a restart.

Draft 2 — durable, but dispatched once

import { appendFileSync } from "node:fs";function publish(event: unknown): void {  appendFileSync("events.log", JSON.stringify(event) + "\n"); // durable  bus.emit("price.changed", event); // still only reaches whoever is listening *now*}

The fact survives a crash in the log. But dispatch is still a one-shot, in-memory broadcast: a consumer that starts five minutes later, or was down when it happened, never sees it. Durability of the fact and delivery to a consumer are two different problems.

Draft 3 — a reader tracks its own position

let offset = 0;function poll(): unknown[] {  const lines = readFileSync("events.log", "utf8").trim().split("\n");  const fresh = lines.slice(offset).map((l) => JSON.parse(l));  offset = lines.length; // remembered *after* processing, not before  return fresh;}

Now a consumer that restarts can resume from its own offset instead of the producer's broadcast moment. But note the comment: if the process crashes after reading a line and before persisting the new offset, that event is redelivered on restart. That's not a bug to fix — it's the origin of "at-least-once."

Draft 4 — acknowledge or redeliver

Give every delivered-but-unacknowledged event a deadline. If it isn't acknowledged before the deadline, hand it out again. That single rule is a broker's visibility timeout (SQS), its consumer group session timeout (Kafka), and its ack-wait (NATS JetStream) — three names for the same fix to the same problem Draft 3 exposed.

DraftWhat it fixesWhat it still can't do
1Reacting to something, at allSurvive a crash
2Surviving a crash (the fact is on disk)Deliver to a consumer that wasn't listening yet
3Resuming after a restartTell the difference between "processed" and "crashed mid-process"
4Redelivering what wasn't acknowledgedGuarantee a redelivery isn't processed twice (§09: idempotency)
03

Delivery guarantees, for real

"At-least-once" and "exactly-once" get repeated as marketing lines. Defined precisely, and checked against what four real systems actually document:

  • At-most-once — delivered zero or one times; a crash between send and receipt loses it silently.
  • At-least-once — delivered one or more times; a crash between processing and acknowledging causes a redelivery. The consumer must tolerate duplicates.
  • Exactly-once — the observed effect happens once, even if the underlying delivery is at-least-once underneath (achieved via deduplication or idempotent writes, not by magically never redelivering).
SystemDefault guaranteeOrdering
KafkaAt-least-once. Exactly-once needs an idempotent producer (enable.idempotence=true) and a transactional consumer (isolation.level=read_committed). Within one partition only (§04).
SQS standardAt-least-once, best-effort — duplicates and reordering both possible.None.
SQS FIFOExactly-once processing via deduplication. Within one Message Group ID only.
SNS standardAt-least-once per subscriber. None across the fanout.
SNS FIFOExactly-once, SQS FIFO subscribers only. Within one message group.
EventBridgeAt-least-once, automatic retry, per-rule DLQ. None.

Sources: Apache Kafka documentation — message delivery semantics; AWS SQS developer guide — FIFO queues; AWS SNS developer guide — FIFO topics; AWS EventBridge user guide.

None of these are run locally on this page — there's no browser-executable "real Kafka" to diff against, the way libuv could be diffed for the event loop page. These rows are quoted from the vendors' own documentation, not independently reproduced.

04

Ordering and partitioning

"The event happened first" and "a consumer sees it first" are different claims. Nothing connects them unless a specific mechanism does.

Kafka orders messages only within a partition. A topic's messages across partitions have no defined relative order at all. A producer picks the partition via a key — same key, same partition, so events for that key are ordered relative to each other, but two different keys give no guarantee either way. SQS FIFO does the equivalent with a Message Group ID instead of a partition key: order is preserved only within one group.

Sandbox — partition key vs. ordering

Emit a few events in each mode, then compare the wide bottom panel against the two above it. With one key everything lands in one partition and arrival order is the order. With mixed keys each SKU stays ordered relative to itself, but the combined view interleaves the two sequences arbitrarily — and that combined order is the only one a consumer of the whole topic sees.

05

What SSE actually is, and what it isn't

Server-Sent Events is not event-driven architecture. It's a transport — one connection, one identified reader, no broker, no fan-out, no durability. Putting it in this page needs a reason, and the reason is the seam: it's where an event-driven system stops talking to itself and starts writing to somebody.

First, the part that really is event-driven

Inside a process, §01's fact 1 is cheap to satisfy. Here is the whole event bus 4th-devs runs its agent system on — a sequence counter, a set of listeners, and a bounded buffer of everything already emitted:

let _seq = 0const listeners = new Set<Listener>()const buffer: AgentEvent[] = []export const emit = (type: string, data = {}): void => {  const event = { seq: ++_seq, type, time: new Date().toISOString(), data }  buffer.push(event)  if (buffer.length > MAX_BUFFER) buffer.shift()  for (const listener of listeners) listener(event)}export const subscribe = (listener: Listener) => {  listeners.add(listener)  return () => { listeners.delete(listener) }}export const replay = (): readonly AgentEvent[] => buffer

Source: 4th-devs, 05_01_agent_graph/src/events.ts.

That is §02's Draft 1 and Draft 2 in about forty lines. emit doesn't know or care who is listening — fact 1, exactly. The bounded buffer plus replay() is a miniature durable log: a listener that attaches late can still be handed everything that already happened. It is the agent system of §07 talking to itself, and it never leaves the process.

Then, the wire

Now the events have to reach a dashboard in a browser, which is a different problem: one specific reader, across a process boundary, over HTTP. That's SSE. One HTTP response that never ends — no upgrade handshake, no new protocol, just Content-Type: text/event-stream on an ordinary response the server keeps writing to, and a client that reads it as a sequence of events instead of one blob. One direction only: server to client. A client that wants to talk back makes a separate, ordinary HTTP request.

The wire format

The body is lines of field: value. A blank line means "dispatch what's buffered so far":

id: 42
event: task.completed
data: {"taskId":"write-intro","actor":"writer"}

data: a plain message with no id or type — dispatched as "message"
  • data: — the payload. Multiple data: lines before a blank line are joined with newlines into one event.
  • event: — the event type a client can filter on with addEventListener(type, ...); omitted, it dispatches as the generic "message" event.
  • id: — the reconnect checkpoint. The browser remembers the last one it saw and resends it as a Last-Event-ID request header if the connection drops and it reconnects.
  • retry: — how many milliseconds to wait before that automatic reconnect.

The seam, in four lines

Here is the same repository's SSE handler, quoted unmodified. Read the last two lines as the join between the two halves of this section — replay() and subscribe() on the left are the in-process bus from above; res.write on the right is one socket belonging to one browser:

res.writeHead(200, {  'content-type': 'text/event-stream',  'cache-control': 'no-cache',  connection: 'keep-alive',})res.flushHeaders()for (const past of replay()) res.write(`data: ${JSON.stringify(past)}\n\n`)const unsubscribe = subscribe(event => res.write(`data: ${JSON.stringify(event)}\n\n`))

Source: 4th-devs, 05_01_agent_graph/src/server.ts (sseHandler).

That adapter is the whole trick, and it's why "is SSE event-driven?" is the wrong question. The bus is event-driven; the socket isn't; subscribe(event => res.write(...)) is the four-word bridge between them. Swap the right-hand side for a Kafka producer and the left-hand side doesn't change — which is exactly what fact 3 (§01) predicted: the coupling that survives is the shape of the event, not who reads it.

Notice it replays every buffered past event on every new connection, unconditionally — it never reads a Last-Event-ID header at all. That's a legitimate, simpler design for a small bounded buffer: the client re-renders from scratch and de-duplicates by id, so exact resumption doesn't need to be the server's job. The client side is equally small:

const es = new EventSource("/events");es.onmessage = (e) => { const ev = JSON.parse(e.data); handleEvent(ev); };

Source: 4th-devs, 05_01_agent_graph/src/dashboard/app.js.

06
AI model streaming as an SSE application

  
"The model streams its response" is section 5, with a schema. Set
  stream: true on an Anthropic Messages API call and the response is exactly a
  text/event-stream, readable by the same EventSource-shaped logic — only
  now the event types and payloads are documented, not ad hoc.

  
One turn is a fixed sequence: message_start (the message shell, with an empty
  content array), then per content block content_block_start →
  repeated content_block_delta → content_block_stop, then
  message_delta (carrying the final stop_reason) and
  message_stop. A ping event may appear between deltas purely as a
  keep-alive, with no content of its own — the same role as the : connected comment
  line a raw SSE server can send.

  
A tool call is a content block whose content_block_start has
  "type": "tool_use" and a partial, growing set of arguments: each
  content_block_delta for that block carries an
  input_json_delta with a partial_json string fragment, not a complete
  value. The fragments must be concatenated and are only guaranteed parseable once
  content_block_stop closes the block — the exact same "buffer until the boundary" rule
  as an SSE data: field in §05, one level up the stack.

07
Agents as event-driven systems

  
An agent's "loop" — plan, act, observe, replan — is a consumer reacting to events:
  its own tool result, another agent's completion, a human answering a question it posed. Wire
  several agents together and the whole system is a graph of tasks reacting to each other's
  done events.

  
A real open-source agent-orchestration course (4th-devs) implements this as a DAG:
  each task lists what it dependsOn; every round, the scheduler recomputes the
  ready set — tasks whose dependencies are all done — and only those run. Its
  round loop is the agent-world analogue of the event loop's phases:

  
    
    
  1. Emit heartbeat.started.
    2. 
    
  2. Reconcile dependency blocks/unblocks.
    3. 
    
  3. Resolve waiting-on-a-human tasks.
    4. 
    
  4. Each agent claims one open task, runs it, the status transition is emitted as an event.
    5. 
    
  5. Emit heartbeat.idle if nothing was claimable, or mark the project done.
    6. 
    
  6. Emit heartbeat.finished; persist a snapshot of the round.
    7.

08
Event sourcing and agent state

  
Nothing so far has stored "the current state" anywhere. It's derived: replay the
  event log from empty, and you have it. That's not an implementation detail — it's a deliberate
  trade of storage simplicity for compute-on-read.

  
4th-devs writes exactly this: an append-only events.jsonl, one JSON
  object per line, that's never edited, only appended to:

  
{"type":"task.completed","round":3,"at":"2026-02-16T12:00:00.000Z", "agent":"writer","taskId":"write-events-section", "data":{"turns":2,"estimated_tokens":1800,"actual_tokens":1690}}

  
Source: 4th-devs, 03_02_events/docs/schemas.md.

  
Two things fall out for free. Crash recovery: restart, replay the log, and the in-memory state is
  exactly what it was — there is no separate "did the state file get corrupted" failure mode, because
  there never was a state file, only the log. Observability: any question about "what happened, and
  when" is answerable by reading the log, not by having remembered to instrument that specific
  question in advance.

  
It doesn't stay free. A log that only ever grows eventually costs more to replay
  than a snapshot would cost to load — which is exactly why Kafka ships log compaction (keeping only
  the latest record per key) as a first-class feature, not an afterthought. Snapshotting is named
  here, not built: out of scope for this page (§11).

    09
    Failure, retries, poison messages
    
  
    Every "at-least-once" system in §03 can redeliver. That's not a bug the consumer
  waits out — it's a contract the consumer must be written for: processing the same event twice has
  to converge to the same result (idempotency), or duplicates corrupt state.
    
  
    The real backoff formula this page's test-model.ts verified against
  4th-devs' recovery.ts:
    
  
    const delay = Math.min(15_000, 1_500 * 2 ** (attempt - 1));// attempt 1: 1500ms  2: 3000ms  3: 6000ms  4: 12000ms  5+: 15000ms (capped)
    
  
    A message that keeps failing past a limit — 4th-devs caps auto-retry at 3 attempts —
  is a poison message: something is genuinely wrong with it, not just transiently unlucky, and
  retrying forever would starve everything behind it. Real brokers name this explicitly: SQS's
  redrive policy moves a message to a dead-letter queue after a configured
  maxReceiveCount; Kafka has no built-in DLQ, so the convention is application-level —
  publish the poison message to a separate <topic>.DLT topic instead of committing
  its offset normally.
    
  
    Sources: AWS SQS developer guide — dead-letter queues; Kafka's
  dead-letter-topic pattern is documented as a convention across Kafka Streams/Connect docs rather
  than a single core-broker feature.
    

  
    
    
    Sandbox — the verified backoff formula, and where it gives up
    
    
    Each click is one more failure. The gaps are the real delays the formula produces — 1500, then 3000, then 6000 ms — and after the third retry the message stops being retried at all and is dead-lettered, because something is wrong with the message, not the timing.

    10
    The dual write: outbox and CDC
    
  
    Every example on this page has quietly cheated. Each one writes something down
  and publishes an event about it, and assumes both happen. They can't — not atomically.
  Your database transaction does not extend to Kafka, and the process can die in the gap.
    
  
    Write first, publish second: the process dies in between, and the order exists while nobody was
  ever told. Publish first, write second: you have announced a fact that isn't true yet, and may
  never become true. There is no ordering of the two calls that fixes this, because the problem isn't
  the order — it's that two separate systems can't agree without a transaction spanning both.
    

  
    The outbox: make it one write
    
  
    Stop trying to do two writes. In the same local transaction that stores the order, insert a row
  into an outbox table describing the event. One transaction, one system, atomic — the
  order and the intent to announce it either both land or neither does. A separate relay then reads
  unpublished outbox rows and pushes them to the broker, marking them sent.
    
  
    The crash doesn't disappear; it becomes survivable. Die before the relay runs and the outbox row
  is still sitting there on restart. Die after publishing but before marking it sent, and the relay
  publishes it twice — which is at-least-once again (§03), and exactly why the consumer has to be
  idempotent (§09). The outbox doesn't buy exactly-once; it buys "never silently lost".
    

  
    CDC: don't write the event at all
    
  
    Change-data-capture answers the same question from the other side. Instead of writing an event
  by hand, read the database's own replication log — Postgres' WAL, MySQL's binlog — and turn each
  committed row change into an event. The write is the event, so there is nothing to keep in
  sync and no outbox table to maintain. Debezium is the usual implementation.
    
  
    The trade is §01's fact 3, collected. With an outbox you choose the event's shape:
  order.placed, carrying the fields you meant. With CDC the shape is whatever your table
  looks like, so a column rename is a breaking change for every consumer — your schema stops being an
  internal detail and becomes the public contract. Cheaper to run, more expensive to evolve.
    

  
    
    
    Sandbox — kill the process between the two writes
    
    
    Tick "crash", place an order, then compare the two modes. Direct mode loses the
    event permanently. Outbox mode survives it, because the pending row is still there for the relay.

    11
    The whole page in rules, and scope
    
  
      
    
    1. A producer doesn't know its consumers; an event is a fact, not a request — a failed consumer
    doesn't un-happen it.
      2. 
    
    2. "At-least-once" is the practical default everywhere (Kafka, SQS standard, EventBridge);
    exactly-once is achieved on top of it via idempotency or dedup, not by avoiding redelivery.
      3. 
    
    3. Ordering is scoped: to a Kafka partition, to an SQS Message Group ID — never to a whole topic
    or queue.
      4. 
    
    4. SSE is one HTTP response the server keeps writing to, in the wire format
    data:/event:/id:/retry:, one direction only.
      5. 
    
    5. AI model streaming is SSE with a documented event schema:
    message_start → per-block content_block_start/delta/stop →
    message_delta → message_stop. Tool-call arguments arrive as JSON
    fragments that are only safe to parse once their block closes.
      6. 
    
    6. A multi-agent system is a DAG reacting to done events; the ready set is
    recomputed every round, the same shape as an event loop's phases one level up.
      7. 
    
    7. Agent state doesn't have to be stored directly — folding an append-only event log recovers it,
    for free, until the log itself needs compaction.
      8. 
    
    8. A consumer under at-least-once delivery must be idempotent; a message that keeps failing past
    a limit belongs in a dead-letter queue, not in an infinite retry loop.
      9. 
    
    9. You cannot write to a database and publish an event atomically. Make it one local write — an
    outbox row in the same transaction, or the replication log itself (CDC) — and let a relay do the
    publishing, or accept that a crash in the gap loses the event silently.
      10. 
  
    
  
    Left out, on purpose
    
  
    The outbox and change-data-capture got a section of their own (§10). Two more a production system hits early, named here rather than half-explained:
    
  
      
    
    • Sagas. Once a workflow spans services, there is no transaction to roll back.
    A saga replaces rollback with explicit compensating actions — refund the payment, release the
    reservation — which means designing the undo for every step, and accepting that the system is
    briefly, visibly inconsistent while it runs.
      • 
    
    • End-to-end exactly-once. §03's exactly-once claims stop at each broker's own
    boundary. Chaining two systems together doesn't compose their guarantees; the joint is where
    duplicates reappear, and idempotency (§09) is the only thing that actually travels.
